# `_workers_next` 顾客管理增强设计

## 1. 背景

当前 `_workers_next` 已有后台顾客列表页 `/admin/users`，但能力明显偏弱：

- 只能看顾客基础列表、积分余额、订单数、最近登录时间。
- 后台修改积分是“直接改成某个值”，没有原因、没有流水、不可审计。
- 顾客维度没有订单明细视图，只能切去后台订单页按订单查。
- 积分获取与消耗来源分散在签到、下单、退款、后台修改等不同入口，缺少统一记账模型。

这会导致两个直接问题：

- 运营无法按顾客维度判断积分为什么变成当前数值。
- 顾客管理页无法承担“顾客账本”角色，查问题仍要在多个后台页面来回跳。

## 2. 目标

本次增强以 `_workers_next` 为唯一目标版本，补齐“顾客详情 + 积分流水 + 顾客订单明细”能力，形成可追溯、可排查、可扩展的顾客管理基础。

最终目标：

- 保留现有顾客列表页，新增顾客详情页 `/admin/users/[id]`。
- 积分调整改为“增加/扣减 + 必填原因”。
- 新增积分流水表，统一记录签到、消费、退款返还、后台调整四类积分事件。
- 顾客详情页可查看顾客基础信息、积分流水、订单列表，并支持订单页内展开查看关键信息。

## 3. 范围

### 3.1 本次范围内

- 新增顾客详情页。
- 新增积分流水表及相关查询。
- 改造积分变动入口，统一走记账服务。
- 改造后台积分调整交互。
- 顾客维度订单列表与页内展开。
- 历史积分数据的可追溯初始化。

### 3.2 明确不在本次范围内

- 不重做现有后台订单详情页 `/admin/orders/[id]`。
- 不增加顾客维度退款、消息、签到的复杂筛选器。
- 不增加积分活动、邀请奖励、补偿发放等新业务类型。
- 不改动前台用户侧页面结构。
- 不引入全套报表、导出、图表统计。

## 4. 推荐方案

采用“列表轻、详情重、账本独立”的方案：

- `/admin/users` 继续作为顾客入口页，只做检索、分页、基础操作。
- 新增 `/admin/users/[id]` 作为顾客详情页。
- 新增积分流水表 `user_point_ledger`，所有积分变化统一入账。
- `login_users.points` 保留为当前余额缓存字段，但不再作为明细来源。
- 顾客详情页展示订单列表，支持页内展开查看关键信息，同时保留跳转现有订单详情页的入口。

选择该方案的原因：

- 能以最小业务重构代价补齐顾客账本能力。
- 结构清晰，后续扩展顾客消息、退款、签到等维度时不会推翻现有设计。
- 避免把 `/admin/users` 堆成“大而杂的表格页”。

## 5. 页面与交互设计

### 5.1 顾客列表页 `/admin/users`

保留现有页面定位，只做两类增强：

- 用户名或用户标识支持点击进入 `/admin/users/[id]`。
- 操作按钮保留“调整积分”“拉黑/解封”。

不在列表页展示积分流水和订单明细，防止列表页失控。

### 5.2 顾客详情页 `/admin/users/[id]`

页面分为四个区块：

#### A. 顾客基础信息卡

展示字段：

- 用户名
- 用户 ID
- 邮箱
- 当前积分
- 是否拉黑
- 注册时间
- 最近登录时间
- 累计订单数

操作入口：

- 调整积分
- 拉黑/解封
- 返回顾客列表

#### B. 积分流水区

默认按时间倒序，展示：

- 流水类型
- 本次变动值
- 变动后余额
- 原因
- 关联订单
- 操作人
- 创建时间

如果流水关联订单，则提供跳转到 `/admin/orders/[id]` 的入口。

首版只做分页与类型标识，不做复杂筛选。

#### C. 顾客订单区

订单列表摘要字段：

- 订单号
- 商品名
- 规格标签（若存在）
- 订单状态
- 订单金额
- 积分抵扣值
- 创建时间

每一行支持展开查看关键信息：

- 联系方式
- 支付流水号
- 创建/支付/发货时间
- 卡密摘要与复制按钮
- 跳转现有后台订单详情页的入口

#### D. 历史说明区

当顾客存在历史初始化积分流水时，页面底部展示说明，明确旧积分是由系统初始化对账产生，而不是完整还原的历史事件。

### 5.3 积分调整弹窗

替换现有“直接改成某个积分值”的交互。

弹窗字段：

- 调整类型：增加 / 扣减
- 调整数值：正整数
- 调整原因：必填
- 调整预览：当前积分 -> 调整后积分

规则：

- 扣减后积分不得小于 0。
- 原因不能为空。
- 成功后刷新顾客详情页积分余额、积分流水和顾客列表积分列。

## 6. 数据设计

### 6.1 新增积分流水表

建议新增表：`user_point_ledger`

字段：

- `id`
- `user_id`
- `event_type`
- `delta`
- `balance_after`
- `business_key`
- `source_type`
- `source_id`
- `reason`
- `operator_user_id`
- `operator_username`
- `metadata`
- `created_at`

建议含义：

- `delta`：积分变动值，正数增加，负数扣减。
- `balance_after`：本次变动后的余额。
- `business_key`：幂等键。
- `source_type`：事件来源类型，如 `checkin`、`order`、`refund`、`admin`。
- `source_id`：来源对象 ID，如订单号。
- `reason`：业务说明，供运营排查。
- `metadata`：少量 JSON 扩展字段，不作为主查询维度。

建议索引：

- `user_id + created_at DESC`
- `business_key` 唯一索引
- `source_type + source_id`

### 6.2 积分事件类型

首版只支持当前系统真实存在的四类事件：

- `checkin_reward`
- `order_deduction`
- `refund_return`
- `admin_adjust`

不提前引入不存在的活动类积分事件，避免过度设计。

### 6.3 当前余额策略

- `login_users.points` 继续保留，作为当前余额缓存字段。
- `user_point_ledger` 作为明细账本。
- 所有积分变化以后必须通过统一服务更新余额并写入流水。

## 7. 历史数据处理

### 7.1 可准确回填的历史事件

可从现有业务数据可靠回填：

- `orders.points_used > 0` -> `order_deduction`
- 订单已退款且 `points_used > 0` -> `refund_return`

### 7.2 不强行伪造的历史事件

以下历史事件目前没有可追溯流水来源，不做伪造回填：

- 历史签到记录对应的具体奖励值
- 历史后台手工改分的每一次操作

### 7.3 历史余额初始化策略

对于旧用户，如果回填后的流水合计无法严格等于当前余额，则补一条初始化流水：

- `event_type = admin_adjust`
- `reason = 历史积分余额初始化`
- `source_type = system`
- `source_id = legacy_balance_init`

目标不是伪造完整历史，而是保证：

- 新系统上线后账本可信
- 旧余额有可解释来源

## 8. 服务层改造

### 8.1 积分服务统一入口

新增统一积分记账服务，禁止业务代码继续直接修改 `login_users.points`。

建议提供以下能力：

- `appendPointLedgerEntry`
- `applyPointDelta`
- `applyCheckinReward`
- `applyOrderPointDeduction`
- `applyRefundPointReturn`
- `applyAdminPointAdjustment`

### 8.2 现有调用点改造

#### 签到

文件：`_workers_next/src/actions/points.ts`

改造为调用 `applyCheckinReward`，由该服务完成：

- 今日签到校验
- 余额增加
- 流水写入

#### 下单积分抵扣

文件：`_workers_next/src/actions/checkout.ts`

改造为调用 `applyOrderPointDeduction`，由该服务完成：

- 可扣减余额校验
- 余额扣减
- 订单关联流水写入

#### 退款返还

文件：

- `_workers_next/src/actions/refund.ts`
- `_workers_next/src/actions/admin-orders.ts`

改造为调用 `applyRefundPointReturn`，统一处理退款返还与幂等控制。

#### 后台手工积分调整

文件：`_workers_next/src/actions/admin-users.ts`

改造为调用 `applyAdminPointAdjustment`。

后台不再传“目标积分值”，而是传：

- 调整类型
- 调整数值
- 调整原因
- 操作人信息

## 9. 幂等与一致性要求

### 9.1 幂等键规则

建议业务幂等键：

- 签到：`checkin:<userId>:<yyyy-mm-dd>`
- 订单抵扣：`order_deduction:<orderId>`
- 退款返还：`refund_return:<orderId>`
- 后台调整：`admin_adjust:<userId>:<timestamp>`

前 3 类必须天然幂等，防止支付回调、退款重试、重复提交导致脏账。

### 9.2 一致性规则

必须保证：

- 任何积分扣减后余额不能为负数。
- 自动积分事件与订单、退款状态一致。
- 后台调整必须有原因。
- 顾客详情页不承担订单状态修改职责。

## 10. 查询与页面数据接口

建议新增以下查询能力：

- `getAdminUserDetail(userId)`
- `getAdminUserPointLedger(userId, page, pageSize)`
- `getAdminUserOrders(userId, page, pageSize)`
- `getAdminUserOrderSummary(orderId)` 或等价页内展开查询

查询原则：

- 顾客详情页使用服务端查询。
- 积分流水分页。
- 顾客订单分页。
- 订单展开优先复用当前页已拿到的数据，避免过深嵌套查询。

## 11. 风险与约束

### 11.1 主要风险

- 现有积分逻辑散落在多个 action 中，若遗漏某个入口，会出现“余额变了但没有流水”。
- 历史数据无法完全还原，只能通过初始化流水解决。
- 当前仓库没有现成测试基础设施，验证主要依赖有针对性的 lint、自检和手动回归。

### 11.2 控制策略

- 所有积分变化统一收口到服务层。
- 在顾客详情页明确标识历史初始化流水。
- 本次只做必要分页和展开，不做复杂筛选与报表。

## 12. 验收标准

满足以下条件视为完成：

- 后台顾客列表可进入顾客详情页。
- 顾客详情页能正确展示顾客基础信息、积分流水和订单列表。
- 订单列表支持页内展开查看关键信息。
- 后台积分调整改为“增加/扣减 + 原因”。
- 签到、下单抵扣、退款返还、后台调整均会写入积分流水。
- 自动事件重复触发时不会重复记账。
- 旧用户能看到可解释的历史初始化积分流水。

## 13. 实施顺序建议

建议按以下顺序实现：

1. 先补积分流水表与统一记账服务。
2. 再改造签到、下单、退款、后台调整入口。
3. 再做顾客详情查询与页面。
4. 最后做顾客列表跳转与交互收尾。

这样可以先把账做对，再做展示层，避免页面完成后发现底层数据不可用。

## 14. 验证策略

由于当前 `_workers_next` 尚无现成测试基础设施，本次以“可重复手动回归 + lint 校验 + 关键幂等场景验证”为主。

关键验证点：

- 后台顾客列表点击用户后能进入顾客详情页。
- 后台执行积分增加时：
  - 当前积分正确增加。
  - 生成一条 `admin_adjust` 流水。
  - 流水中带有原因、操作人、变动后余额。
- 后台执行积分扣减时：
  - 不允许扣成负数。
  - 成功后余额与流水一致。
- 用户签到时：
  - 当天首次签到生成一条 `checkin_reward` 流水。
  - 同一天重复签到不会重复生成流水。
- 使用积分下单时：
  - 订单写入 `points_used`。
  - 生成一条 `order_deduction` 流水。
  - 重试或重复触发时不会重复记账。
- 积分抵扣订单退款时：
  - 余额正确返还。
  - 生成一条 `refund_return` 流水。
  - 重复退款处理不会重复返还积分。
- 历史用户进入顾客详情页时：
  - 能看到历史初始化积分流水或可还原历史流水。
  - 当前积分与详情页头部展示一致。
- 顾客详情页订单区展开时：
  - 能正确展示状态、金额、积分抵扣、联系方式、时间和卡密摘要。
  - 能跳转到现有 `/admin/orders/[id]`。
