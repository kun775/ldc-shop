# `_workers_next` 商品表单保存 Loading 遮罩设计

## 1. 背景

当前 `_workers_next` 后台商品新建/编辑页共用同一个商品表单组件：

- 新建页：`/admin/product/new`
- 编辑页：`/admin/product/edit/[id]`

这两个页面在点击“保存商品”后，虽然内部已经存在基础的 `loading` 状态，但用户侧反馈非常弱，体感上容易出现以下问题：

- 点击保存后像“没点到”
- 页面没有明显忙碌反馈
- 表单仍然停留在原位，用户很难判断是否已经开始提交
- 慢操作期间容易重复点击或继续修改表单

用户已经明确指出，当前问题的核心不是“保存逻辑错误”，而是“提交过程缺少足够强的可见反馈”。

因此，本次目标是给商品表单增加明确的局部 loading 遮罩，让用户在点击保存后立刻感知到系统正在处理。

## 2. 目标

本次仅增强商品表单保存时的交互反馈，不改商品保存业务逻辑。

目标如下：

- 点击“保存商品”后，商品表单区域立即出现明显的 loading 遮罩
- 提交过程中锁定商品表单，避免重复点击和误操作
- 保存成功后保持现有成功提示和跳转行为
- 保存失败后保持现有错误提示，并恢复表单可操作状态
- 新建商品页和编辑商品页同时生效

## 3. 范围

### 3.1 本次范围内

- `_workers_next` 商品新建/编辑共用表单的保存交互
- 商品表单卡片级 loading 遮罩
- 提交期间的按钮和表单锁定

### 3.2 不在本次范围内

- 不修改 `saveProduct()` 的业务校验、入库、回源和缓存刷新逻辑
- 不修改商品保存成功后的跳转目标
- 不改店铺设置、加卡、订单管理等其他后台慢操作页面
- 不新增全局 loading 管理器
- 不做全屏遮罩

## 4. 现状分析

当前商品表单位于：

- `_workers_next/src/components/admin/product-form.tsx`

现有实现特点：

- 表单内部已经有 `loading` 状态
- 保存按钮已经有 `disabled={loading}` 和 `saving` 文案
- 但当前反馈只集中在提交按钮本身
- 对整个表单区域没有明确的“正在保存”视觉提示
- 用户在慢请求期间仍会感知为“页面没反应”

这说明问题不在于是否有布尔状态，而在于反馈层级太低、可见性太差。

## 5. 选型结论

本次采用“表单卡片级 loading 遮罩”的方案，不做全页遮罩。

### 5.1 为什么不用只改按钮

仅把按钮改成 `disabled + saving...` 的方式，当前项目其实已经部分具备，但用户仍然觉得“像没点到”，说明这个层级的反馈不足以解决问题。

### 5.2 为什么不用全页遮罩

全页遮罩虽然反馈更强，但会把后台侧边栏和其他区域一起锁死，影响范围过大，不符合本次“只修商品表单保存体验”的目标。

### 5.3 推荐方案

采用局部遮罩：

- 只覆盖商品表单卡片内容区域
- 遮罩出现后，商品表单整体进入不可操作状态
- 页面其余区域仍保持原状

这样可以在不扩大改动面的前提下，显著提升提交反馈强度。

## 6. 交互设计

### 6.1 触发时机

仅在用户点击“保存商品”且真正开始提交后显示遮罩。

以下场景不触发本次遮罩：

- 页面初始加载
- 图片选择与本地压缩处理
- 普通输入和切换选项

### 6.2 遮罩范围

遮罩只覆盖商品表单所在卡片内容区，不覆盖：

- 后台页面顶部标题
- 左侧导航
- 整个后台页面外层容器

### 6.3 遮罩表现

遮罩表现采用轻量但明确的样式：

- 半透明蒙层
- 适度模糊背景
- 居中 loading 图标
- 居中提示文案，例如“保存中...”

文案优先复用现有国际化 key，避免为本次需求引入不必要的新文案结构。

### 6.4 提交期间锁定行为

当遮罩出现时，商品表单整体不可再操作，包括但不限于：

- 保存按钮
- 返回按钮
- 输入框
- 文本域
- 复选框
- 图片上传按钮
- 图库操作按钮

本次目标不是只禁止二次点击保存，而是让用户明确进入“当前正在提交，请等待结果”的状态。

### 6.5 结束行为

#### 保存成功

- 保持现有成功 toast
- 保持现有跳转到 `/admin/products` 的逻辑

#### 保存失败

- 保持现有错误 toast
- 立即解除遮罩
- 保留当前表单内容，便于用户继续修正

## 7. 实现设计

### 7.1 主改文件

本次核心只改：

- `_workers_next/src/components/admin/product-form.tsx`

原因：

- 商品新建页和编辑页共用这个组件
- 页面级文件只是透传数据，不负责保存交互
- 把改动集中在表单组件能保证影响面最小

### 7.2 提交流程调整

当前表单使用的是直接绑定提交逻辑的表单提交方式。

本次推荐把提交入口收敛为更明确的客户端提交流程：

- 在提交事件里显式构造 `FormData`
- 在客户端第一时间切换 `loading`
- 然后调用现有 `saveProduct()` server action

这样做的目的不是改业务，而是确保“点击后立刻进入稳定的 pending UI”，让表单遮罩和锁定行为更可靠。

### 7.3 视觉实现

表单卡片内容区增加一个与 `loading` 状态联动的覆盖层：

- `loading = false` 时不显示
- `loading = true` 时显示遮罩层

同时为表单根容器增加与 `loading` 联动的锁定表现，使用户视觉和交互都能明确感知“正在保存”。

### 7.4 现有逻辑保持不变

以下逻辑不应因为本次需求发生行为变化：

- 商品字段收集
- 图片主图/图库整理逻辑
- 积分抵扣配置保存逻辑
- `saveProduct()` 内部数据库写入
- 成功后跳转
- 失败后错误提示

## 8. 国际化策略

优先复用已有通用文案，避免无必要新增 key。

已确认项目中已有类似文案：

- `admin.productForm.saving`
- `common.loading`
- `common.processing`

本次设计优先使用 `admin.productForm.saving` 作为遮罩主提示，保持上下文一致。

## 9. 风险与约束

### 9.1 不扩散到其他后台页面

这次只处理商品表单保存反馈，不把问题扩大成“后台所有慢操作统一 loading 框架”。

### 9.2 不改后端保存逻辑

本次是前端交互增强，不应该顺手动 `saveProduct()` 的业务逻辑，否则范围会失控。

### 9.3 失败时必须释放锁定

如果保存失败后遮罩未解除，用户会被卡死在表单页，因此 `finally` 分支必须可靠恢复可交互状态。

### 9.4 本地图片处理不纳入本次遮罩

商品图片选择后，本地压缩本身已有单独状态，本次不把这些处理统一并入“保存商品遮罩”，避免把多个不同阶段的 loading 混成一个状态。

## 10. 验证要求

至少验证以下场景：

- 在新建商品页点击“保存商品”时，表单卡片区域立即出现遮罩
- 在编辑商品页点击“保存商品”时，表单卡片区域立即出现遮罩
- 遮罩显示时，保存按钮不可重复点击
- 遮罩显示时，返回按钮和表单输入区都不可继续操作
- 保存成功后仍跳转回 `/admin/products`
- 保存失败后遮罩消失，表单内容保留
- 本次改动不影响现有商品保存逻辑

## 11. 结论

本次需求的本质不是新增商品能力，而是修复“后台慢操作反馈太弱”的体验问题。

最合适的改法是：

- 只处理商品表单
- 只做卡片级遮罩
- 不动后端业务
- 让保存动作在点击后立刻给出明确、稳定、不可误解的反馈

这样改动小、收益直接，也符合当前 `_workers_next` 版本的维护策略。
