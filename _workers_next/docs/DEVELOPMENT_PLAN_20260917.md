# 后台稳定性、加载体验与审计模块开发计划

更新日期：2026-09-17

## 一、总体目标

1. 保证 Cloudflare D1 数据库结构能够由管理员在后台手动、幂等升级，并可查看执行状态、错误 ID 和重试结果；代码部署和普通页面访问不得自动迁移。
2. 修复优惠券编辑与后台积分调整中的服务端异常，确保失败可恢复、可追踪，不再出现无信息的“错误”或整页崩溃。
3. 增加统一的页面 Loading 遮罩，避免页面首次加载、路由切换或服务端数据加载较慢时长时间显示空白页面。
4. 修复手动发货确认提交时的异常遮罩问题，确保成功、失败和超时场景都能正确释放提交状态。
5. 新增后台审计模块，记录用户操作和平台运行错误，并提供筛选、分页、详情与处理状态。

## 三、阶段一：数据库升级管理（已完成）

### 已实现内容

- 建立版本化升级清单和 `database_migrations` 执行记录表。
- 升级记录包含状态、声明 ID、开始时间、完成时间、耗时、错误 ID 和更新时间。
- 升级使用数据库声明机制控制并发，避免多个 Worker 实例重复执行同一升级。
- 升级执行失败时停止后续步骤，不提前写入成功状态或最新 schema 版本。
- 升级成功后再次执行结构自检，只有真实结构完整才登记为 `applied`。
- 将普通请求初始化与数据库升级执行彻底分离；`ensureDatabaseInitialized()` 只检查基础表可读，不执行 DDL、注册迁移或 schema 版本写入。
- 注册升级仅由 `/admin/database` 的管理员操作触发，页面加载和状态刷新不会执行待升级项。
- 新增 `/admin/database` 管理页面，支持刷新状态、执行升级和重试失败项。
- 修复 schema 27 升级到 schema 28 时重复执行全量迁移的问题。
- 修正积分账本结构探测字段，将错误的 `operator_id` 改为真实字段 `operator_user_id`。
- 保留对历史数据库缺表、缺列、缺索引和缺触发器的幂等修复能力。

### 完成验证

- 生产数据库 `schema_version` 已更新为 `28`。
- `0028_database_upgrade_registry` 状态已更新为 `applied`。
- 最终升级耗时约 2.3 秒，历史错误 ID 已清空。
- 已验证关键表、字段和 11 个业务触发器均存在。
- 已升级数据库不会重复执行结构修复；检测到真实结构漂移时仍允许重新修复。
- 单元测试、TypeScript 检查、ESLint、Next.js 生产构建和 Worker dry-run 已通过。

### 后续维护要求

- 每个新增数据库变更必须新增独立升级项，不得继续把所有 DDL 堆叠到一个全量升级函数中。
- 升级项必须具备唯一、递增且不可复用的 ID，并明确对应的最低 schema 基线。
- 结构探测字段必须直接对应真实 schema，并增加测试防止探测字段与表定义漂移。
- 数据修复和大批量回填应与轻量 DDL 分开，避免单次 Worker 请求超时。
- 禁止依赖手工登录生产 D1 执行 SQL；生产迁移必须通过后台数据库升级页面由管理员显式执行。

## 四、阶段二：优惠券编辑故障修复

### 开发内容

- 完善优惠券主表、关联商品表、使用记录表和用户计数表的缺表、缺列及索引漂移识别。
- 优惠券读取失败时，仅在确认属于结构问题后执行一次幂等结构修复并重试。
- 区分“优惠券不存在”和“数据库查询异常”，避免把系统错误转换成 404。
- 收口创建、编辑、状态切换、复制和删除操作的异常，统一返回安全文案与可复制错误 ID。
- 为优惠券编辑路由增加错误边界，单个模块异常不得导致整个后台布局崩溃。
- 检查优惠券表单初始值、时间字段、商品范围和可叠加规则，避免历史数据为空时触发渲染异常。

### 验收标准

- 新建、打开、编辑、保存、启停、复制和删除优惠券均可正常完成。
- 历史数据库结构不完整时能够自动修复一次并恢复操作。
- 优惠券不存在时显示明确的不存在状态；数据库错误显示安全文案和错误 ID。
- 服务端异常不会出现整页 “This page couldn't load” 或无限 Loading。

## 五、阶段三：积分调整故障修复

### 开发内容

- 校验 `login_users`、`user_point_ledger` 的必要字段、索引和余额触发器。
- 从 `sqlite_master` 校验积分触发器是否存在，定义升级时使用新的迁移项重建。
- 覆盖增加积分、扣减积分、余额不足、重复业务键和并发调整场景。
- 所有积分变更必须写入账本，并保证余额变更与账本完成状态一致。
- 后台调整失败时释放提交状态，保留输入内容并显示安全错误文案和错误 ID。
- 避免客户端重复提交造成两次积分变更。

### 验收标准

- 后台增加或扣减积分后余额和账本记录立即一致。
- 余额不足时不产生部分写入，不出现负数余额。
- 相同业务键重复请求不会重复记账。
- 调整失败时页面可继续操作，按钮和遮罩能够恢复，不再只显示“错误”。

## 六、阶段四：页面 Loading 遮罩

### 目标范围

- 覆盖页面首次进入、后台页面切换和服务端数据加载阶段，避免用户长时间看到空白页面。
- Loading 遮罩只表示页面级导航或数据装载，不接管保存、删除、发货等业务提交状态。
- 优先复用现有布局、主题变量和组件样式，不引入新的重型动画或依赖。

### 交互设计

- 页面加载超过短暂阈值后显示全屏遮罩，快速响应时不闪烁。
- 遮罩包含明确的加载指示和简短状态文案，不显示业务成功或失败结论。
- 遮罩层使用稳定的固定定位和统一层级，覆盖页面内容但不造成布局位移。
- 遮罩显示期间阻止对下层页面重复点击；结束后必须恢复滚动和交互。
- 支持浅色、深色主题和移动端安全区域，避免遮挡后留下不可点击透明层。
- 使用 `aria-busy`、`aria-live` 或等效语义向辅助技术说明加载状态。
- 尊重减少动态效果设置，Loading 动画不得成为页面性能瓶颈。

### 状态与异常处理

- 明确区分 `idle`、`delayed`、`loading`、`completed` 和 `failed` 状态。
- 路由完成、组件卸载、错误边界接管和请求失败时都必须释放遮罩。
- 多个并发加载任务需要采用引用计数或唯一任务标识，禁止较早请求错误关闭仍在使用的遮罩。
- 设置防永久遮罩保护：超过预期时长后切换为可恢复提示，而不是无限旋转。
- 页面发生服务端错误时由错误边界展示错误信息，Loading 遮罩不得覆盖错误界面。
- 与对话框、抽屉和表单提交遮罩定义明确的层级规则，避免双层遮罩叠加。

### 验收场景

- 在慢速网络下进入首页、商品列表、订单列表、顾客列表和数据库升级页面，加载期间不出现纯空白页面。
- 正常网络快速切换页面时不出现明显闪烁。
- 页面加载成功、失败、返回上一页和快速连续导航后，遮罩都能正确消失。
- 桌面端和移动端均无内容跳动、滚动锁残留或透明层阻塞点击。
- 页面级 Loading 不影响按钮自身的提交中状态。

## 七、阶段五：手动发货确认提交遮罩修复

### 问题范围

- 手动发货确认提交后出现异常遮罩、遮罩不消失、页面无法继续点击或错误状态被遮罩覆盖。
- 快速重复点击可能产生多个请求，使较早请求和较晚请求互相覆盖提交状态。
- 服务端提交失败、网络异常或页面刷新时，客户端状态可能未进入统一的清理流程。

### 修复方案

- 梳理手动发货确认对话框、提交按钮、Server Action 和页面刷新之间的完整调用链。
- 将提交状态明确划分为 `idle`、`submitting`、`success` 和 `error`，禁止使用多个互不关联的布尔值控制同一遮罩。
- 提交开始时锁定确认按钮并阻止重复提交，同一次操作只允许存在一个有效请求。
- 使用统一的 `try/catch/finally` 或等效机制，成功、业务失败、网络失败和异常抛出后都必须释放遮罩。
- 提交成功后关闭确认对话框，刷新订单数据并展示成功反馈。
- 提交失败时保留已填写的发货内容，解除遮罩和按钮禁用状态，展示安全错误文案及错误 ID。
- 页面卸载或对话框关闭后忽略迟到响应，避免已关闭界面重新挂载遮罩。
- 手动发货提交遮罩限定在当前业务区域，不能与页面级 Loading 遮罩重复占用全屏层级。
- 统一遮罩的 `z-index`、`pointer-events` 和滚动锁释放逻辑，防止视觉上消失但仍拦截点击。

### 回归测试

- 正常确认发货：只提交一次，订单状态和发货信息更新，遮罩正常消失。
- 服务端业务校验失败：不修改订单，保留输入，显示错误，遮罩和按钮恢复。
- Server Action 抛出异常：显示通用错误和错误 ID，页面仍可继续操作。
- 网络超时或中断：进入可恢复错误状态，不出现永久遮罩。
- 连续快速点击确认：只产生一个有效请求，不重复发货。
- 提交期间切换页面或关闭对话框：无状态更新警告，无透明遮罩残留。
- 与页面 Loading 同时发生时，只保留正确层级的单一可见遮罩。

### 验收标准

- 手动发货成功和失败后均不会留下全屏或透明异常遮罩。
- 遮罩存在时能够明确说明正在提交，结束后交互能力完整恢复。
- 提交失败不丢失管理员已填写的发货备注或相关输入。
- 重复点击不会产生重复发货、重复消息或重复审计记录。

## 八、阶段六：审计基础设施

### 数据模型

- 新增 `audit_events`，记录登录、签到、下单、退款及管理员操作。
- 新增 `platform_error_logs`，记录错误 ID、范围、严重级别、脱敏错误链、请求信息和处理状态。
- 为时间、事件类型、用户 ID、目标类型、目标 ID、结果、严重级别和错误 ID 建立查询索引。
- 审计记录只允许追加；处理状态和处理说明使用独立字段更新，不允许篡改原始事件内容。

### 写入约束

- 日志写入采用 best-effort，审计服务失败不得覆盖原业务结果或递归记录自身错误。
- 为登录、签到、下单、退款和管理员写操作定义稳定的事件名称和字段结构。
- 对 Token、Cookie、Authorization、支付密钥、卡密、SQL 参数、邮箱和 IP 等信息进行脱敏或哈希处理。
- 控制上下文和堆栈长度，避免单条错误日志超过 D1 写入限制。
- 为相同错误短时间高频发生设计聚合或限流策略，防止日志写入放大故障。

## 九、阶段七：审计业务接入与后台页面

### 业务接入

- 接入 `refund.requested`、`refund.approved`、`refund.rejected`、`refund.completed`。

- 对成功和失败结果使用统一字段，保留目标 ID、操作人和错误 ID 关联。

### 后台页面

- 新增 `/admin/audit`，提供“用户操作”和“平台错误”两个视图。
- 支持按时间、事件类型、用户、目标 ID、结果、严重级别和错误 ID 筛选。
- 使用服务端分页和稳定排序，不一次性加载全部日志。
- 平台错误支持标记已处理和填写处理说明。
- 详情页面只展示脱敏信息，不提供直接修改原始审计记录的能力。
- 审计列表加载接入页面 Loading 方案，并提供空状态、错误状态和重试入口。

## 十、实施顺序与提交批次

1. `docs(plan): 细化稳定性与审计开发计划`：本次仅更新计划文档。
2. `feat(ui): 新增页面加载遮罩`：完成页面级 Loading、错误释放和移动端适配。
3. `fix(orders): 修复手动发货提交遮罩状态`：修复提交生命周期、重复提交和异常清理。
4. `fix(coupons): 完成优惠券编辑全流程回归`：补齐历史结构和异常边界验证。
5. `fix(points): 完成积分调整全流程回归`：验证账本、余额和并发幂等。
6. `feat(audit): 新增操作审计与平台错误日志`：完成数据模型和统一写入接口。
7. `feat(admin): 新增审计管理页面`：完成筛选、分页、详情和处理状态。

已完成的数据库升级相关提交继续保留，不再重复创建同一升级项。所有代码提交推送到 `main` 后由现有 Cloudflare Git 集成自动部署，不执行手工 Worker 部署；部署完成后由管理员进入后台数据库页面确认并执行待升级项。

## 十一、数据库与部署约束

- 数据库为 Cloudflare D1，代码部署不得自动修改数据库结构；生产升级由管理员在后台数据库升级页面手动触发，不能依赖手工执行 SQL。
- 升级只能在对应步骤完整成功后登记为已执行；失败记录必须允许管理员重试。
- 新增表和列优先采用向前兼容设计，旧代码回滚后允许新增结构保留。
- 当前 Cloudflare 免费账户 Cron Trigger 已达到上限，不为日志清理新增 Cron；后续复用现有 cleanup 入口。
- 页面 Loading 和业务提交遮罩不得触发额外数据库请求，也不得改变数据库迁移时序。
- 手动发货、积分和优惠券等写操作必须保持幂等，失败后不得留下部分业务状态。

## 十二、总体验收标准

- 数据库升级页面能够显示所有注册升级项；重复访问页面或访问首页不会执行升级。
- 历史数据库缺表或缺列时，管理员手动升级和后台重试能够恢复结构并留下可追踪记录。
- 页面首次加载和路由切换期间不再出现长时间空白，成功或失败后无永久遮罩。
- 手动发货确认提交成功、失败、超时和重复点击场景均无异常遮罩或重复写入。
- 优惠券可以正常打开、编辑和保存；积分增减立即生效且余额正确。
- 审计后台可以查询登录、签到、下单、退款、手动发货和管理员操作。
- 平台错误可以通过错误 ID 查询并标记处理，日志中不包含敏感凭据或原始 SQL 参数。
- 所有新增前端状态覆盖加载、空数据、失败、重试和权限不足场景。
- 合并前通过受影响测试、TypeScript 检查、ESLint 和生产构建。
