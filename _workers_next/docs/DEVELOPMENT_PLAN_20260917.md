# 后台稳定性与审计模块开发计划

更新日期：2026-09-17

## 目标

1. 修复优惠券编辑页服务端异常，确保历史数据库结构不完整时能够自动修复并给出可追踪错误。
2. 修复后台积分调整失败，确保积分账本表、索引与触发器能够按当前定义自动升级。
3. 新增后台审计模块，记录用户操作和平台错误日志，并提供筛选、分页、详情及处理状态。
4. 新增后台数据库升级管理模块，集中展示升级状态、执行待升级项，并在 Worker 首次访问时自动执行待完成升级。

## 执行顺序

### 第一阶段：数据库升级管理

- 建立版本化升级清单和 `database_migrations` 执行记录表。
- 所有升级使用幂等 DDL，并在成功完成结构校验后写入已执行状态。
- 接入现有 `ensureDatabaseInitialized()`，部署新 Worker 后自动执行待升级项。
- 新增 `/admin/database` 管理页面，展示总升级数、已执行、待执行、失败原因和错误 ID。
- 管理员可以刷新状态、执行或重试待升级项；并发执行通过数据库声明机制避免重复运行。
- 升级执行失败时停止后续升级，不把数据库标记为已就绪。

### 第二阶段：优惠券编辑故障修复

- 完善优惠券缺表、缺列、索引和关联表结构漂移识别。
- 读取失败时自动执行一次优惠券结构修复并重试。
- 区分优惠券不存在和数据库异常，避免把系统错误转换成 404。
- 收口创建、编辑、状态切换、复制和删除操作的异常，统一返回安全错误文案与错误 ID。
- 增加优惠券编辑路由错误边界，避免单个模块异常导致整个后台页面崩溃。

### 第三阶段：积分调整故障修复

- 校验 `login_users`、`user_point_ledger` 的必要列和索引。
- 从 `sqlite_master` 校验积分触发器定义；定义过期时按新版本自动重建。
- 增加积分账本迁移版本，覆盖增加、扣减、余额不足、重复业务键和并发执行。
- 后台调整失败时显示可复制错误 ID，不再只显示“错误”。

### 第四阶段：审计基础设施

- 新增 `audit_events`，记录登录、签到、下单、退款及管理员操作。
- 新增 `platform_error_logs`，记录错误 ID、范围、严重级别、脱敏错误链、请求信息和处理状态。
- 日志写入采用 best-effort，日志服务失败不得覆盖原业务结果或递归记录自身错误。
- 对 Token、Cookie、Authorization、支付密钥、卡密、SQL 参数、邮箱和 IP 等信息进行脱敏或哈希处理。

### 第五阶段：审计业务接入与后台页面

- 接入 `auth.login`、`points.checkin`、`order.created`。
- 接入 `refund.requested`、`refund.approved`、`refund.rejected`、`refund.completed`。
- 接入 `admin.points.adjusted`、`coupon.created`、`coupon.updated` 等管理员操作。
- 新增 `/admin/audit`，提供“用户操作”和“平台错误”两个视图。
- 支持按时间、事件类型、用户、目标 ID、结果、严重级别和错误 ID筛选，并使用服务端分页。
- 平台错误支持标记已处理和填写处理说明，不提供直接篡改单条审计记录的能力。

## 数据库与部署约束

- 数据库为 Cloudflare D1，生产升级必须随代码部署自动完成，不能依赖手工登录执行 SQL。
- 升级只能在对应步骤完整成功后登记为已执行；失败记录必须允许管理员重试。
- 新增表和列优先采用向前兼容设计，旧代码回滚后允许新增结构保留。
- 当前 Cloudflare 免费账户 Cron Trigger 已达到上限，不为日志清理新增 Cron；后续复用现有 cleanup 入口。
- 代码按以下批次提交并由推送自动触发 Worker 部署：
  1. `feat(admin): 新增数据库升级管理`
  2. `fix(coupons): 修复编辑页结构漂移与异常处理`
  3. `fix(points): 修复积分调整并增加错误追踪`
  4. `feat(audit): 新增操作审计与平台错误日志`

## 验证标准

- 已升级数据库不重复执行升级，并发点击不会重复运行同一升级。
- 历史数据库缺表或缺列时，自动升级和后台手动升级都能恢复结构。
- 升级失败后页面仍可打开，能够看到安全错误文案和错误 ID并执行重试。
- 优惠券可以正常打开、编辑和保存；积分增减立即生效且余额正确。
- 审计后台可以查询登录、签到、下单、退款和管理员操作。
- 日志中不包含卡密、支付凭据、Cookie、Token 或原始 SQL 参数。
- 合并前通过类型检查、ESLint、单元测试和生产构建。
